# 5. Riscos e mitigações

Matriz de riscos do projeto contratado, priorizada por impacto × probabilidade. "Mitigação já prototipada" indica que a prévia técnica já contém o mecanismo, não apenas o plano.

| # | Risco | Impacto | Probabilidade | Mitigação |
|---|---|---|---|---|
| R1 | Requisitos de dados (RD-01–RD-07) não são atendidos a tempo pelo cliente (semântica de classes, unidade física, RPM, etc.) | Alto (sem isso o projeto não sai do nível "padrões", nunca chega a "falhas" nomeadas) | Média | Fase 0 formalmente bloqueante (marco M0); enquanto isso, **busca de datasets públicos com configuração similar** (CWRU, MFPT, Paderborn, MaFaulDa, ver `06_track_pesquisa.md`) para manter o pipeline evoluindo sem parar a equipe |
| R2 | Sensores em campo falham, saturam ou geram ruído (o próprio enunciado já avisa disso) | Alto (decisão automática sobre dado ruim é pior que nenhuma decisão) | Alta (já observado nos dados fornecidos: `Dados_4` travado, `Dados_5` ruído) | **Já prototipado**: `data/audit.py` roda a cada novo lote de dados (`GET /audit`), re-decidindo quais sensores merecem confiança; janelas quase silenciosas são sinalizadas (`is_silent`) e tratadas com abstenção, não com predição forçada |
| R3 | Prior de classes em produção é muito diferente do prior balanceado do case (operação normal domina) | Médio-Alto (métricas de teste otimistas não se sustentam em produção) | Alta | **Já prototipado**: `evaluation/imbalance.py` reavalia sob um prior configurável (`configs/default.yaml: imbalance.simulated_prior`); RD-06 pede dados reais de prior assim que disponíveis |
| R4 | Classes nunca vistas em treino aparecem em produção (nova falha, degradação atípica) | Alto (um classificador fechado força a classe mais parecida, mesmo quando errado) | Média | Track de pesquisa H4/H8 (`06_track_pesquisa.md`): reconhecimento *open-set*/detecção de anomalia baseada em resíduos; enquanto isso, o **conjunto de predição conformal já sinaliza baixa confiança** quando a janela não se parece com nenhuma classe treinada |
| R5 | Modelo degrada silenciosamente com o desgaste natural da máquina ou após manutenção corretiva (drift de conceito) | Alto (o pior cenário é confiança errada, não incerteza) | Alta ao longo do tempo | **Já prototipado**: `evaluation/drift.py` (PSI + Kolmogorov-Smirnov) + `GET /drift`; gatilho de retrain formalizado em `09_mlops.md` |
| R6 | Modelo interpretado como "caixa preta" pelo time de manutenção, gerando resistência de adoção | Médio | Média | Árvore de decisão como baseline explicável, SHAP/LIME por predição (`evaluation/explain.py`, `POST /explain`) e validação conjunta com o time de manutenção |
| R7 | Overfitting ao conjunto curado do case (balanceado, sem os problemas reais de uma planta) | Médio | Média (mitigado, não eliminado, pela prévia) | Split treino/calibração/teste com limpeza ajustada só no treino (ver `03_arquitetura.md`, seção 3.3); controles de embaralhamento e sensor-ruído confirmam ausência de vazamento nesta amostra (mas a validação final só acontece com dados reais do cliente (Fase 1–2)) |
| R8 | Latência/carga de inferência em escala de planta (muitos sensores, muitas máquinas) não avaliada nesta prévia | Médio | Baixa no piloto, cresce com escala | Modelo raso (árvore/ensemble) tem custo de inferência desprezível comparado a deep learning; arquitetura de API já é *stateless* e horizontalmente escalável (FastAPI + banco compartilhado) |
| R9 | Dependências de terceiros com requisitos de compilação nem sempre atendidos por toda imagem de implantação (ex.: MLflow/SHAP/ssqueezepy exigem toolchain C/C++) | Baixo-Médio | Confirmada nesta prévia | **Já resolvido com fallback documentado** em cada módulo afetado (ver `03_arquitetura.md`, seção 3.6): nenhuma decisão de arquitetura de produção depende de uma dependência opcional estar presente |
| R10 | Rotatividade/disponibilidade da equipe do cliente para validar semântica de classes e dar feedback de campo | Médio | Média | Marcos formais de validação conjunta (M1, M2, M5) em vez de aprovação implícita; documentação de requisitos (`02_engenharia_requisitos.md`) serve como registro do que foi combinado |

## Princípio geral de mitigação

Onde foi possível, a prévia técnica não apenas *lista* um risco: ela **entrega o mecanismo de mitigação já funcionando** (R2, R3, R5, R6, R7, R9). Isso é deliberado: um plano de risco convence mais quando o item "mitigado" aponta para código testado, não para uma promessa de fase futura.
